# Session Host Monitoring Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

[中文版本](2026-09-26-session-monitoring_zh.md)

**Goal:** Show live Linux host resource metrics on the selected connection page, with independently disposable Host/Client monitoring plugins.

**Architecture:** HostMonitor uses the existing authenticated SSH connection and publishes typed updates through the public Host facade, dispatcher, and WebSocket. ClientMonitor owns the panel and visibility/subscription lifecycle. Session facts take a separate path: `SshService` records the ssh2 handshake result, `TerminalBridge` publishes it as `session:facts`, and `ClientChrome` renders it in the status bar, so the monitor plugin is never the owner of a fact about a session it merely observes. Terminal, SFTP, and application readiness have no dependency on monitoring.

**Tech Stack:** Existing TypeScript, Cordis, ssh2, browser DOM/CSS tokens, Node test runner, and Electron lifecycle fixtures. No new runtime dependency.

**Spec:** [Session Host Monitoring Design](../specs/2026-09-26-session-monitoring-design.md). Read it completely; its contracts, numeric semantics, and defaults are normative for this plan.

**Status:** Unexecuted handoff, 2026-09-26. This document records proposed work, not existing behavior or passing feature tests. Code snapshot: `feat/ui-redesign` at `87ae9e2`; the monitoring documents themselves landed on top of it at `a305810`. The user asked this task to write documentation for other agents; this task does not implement or publish the feature.

## Global Constraints

- Node.js 24 or newer; PowerShell on Windows; UTF-8; commands below run from the repository root.
- Linux remote MVP; polled metrics are CPU, memory, load 1/5/15, the root filesystem, network throughput, and the remote host's own uptime. Session facts — the negotiated cipher pair and the server host key algorithm — are **not** polled and are not part of a snapshot (Task 2). The metric list is otherwise documented planning defaults, subject to a later user correction.
- The expansion carries only what a screen renders. The prototype's status bar cell reads `chacha20-poly1305 · ed25519 · 128 行`, which is cipher, host key and terminal size, so the key-exchange algorithm and the remote software version are deliberately **not** carried: nothing would display them. The software token is additionally unreachable without reading a private ssh2 field (`Client` keeps it as `this._remoteVer`, `node_modules/ssh2/lib/client.js:318`), so carrying it would make its only test a test of a private field.
- Three parts of this expansion are explicit user decisions, not planning defaults: uptime means the remote **host's** uptime rather than the session's, throughput sums every non-loopback interface, and the handshake facts travel on their own channel instead of riding a snapshot.
- Refresh: immediately, then 5,000 ms after probe completion. Exec timeout: 3,000 ms including channel acquisition. Combined stdout/stderr limit: 65,536 bytes. Active-data stale threshold: 15,000 ms.
- Only the selected connected tab with visible document, expanded panel, and no manual pause may collect. At most one active subscription per client, with no overlapping local probes per session. The panel defaults to collapsed, so a freshly opened session collects nothing until the user expands it; collapsing retires the subscription rather than leaving it running invisibly. Session facts are exempt from all of this: they are emitted once per handshake and again on rekey, with no subscription, no timer, and no visibility gate.
- Static Cordis composition; existing SSH connection; no remote agent, sudo, arbitrary commands, new HTTP endpoint, Electron business IPC, history storage, or npm plugin loader.
- Follow AGENTS.md dependency boundaries and paired English/Chinese documentation. Keep this design's exact interfaces consistent across tasks.
- Before executing, inspect current branch/worktree and AGENTS.md. Preserve unrelated work, including the four `design-qa-*.png` files present at the inspected baseline. Follow the repository's branch policy; this plan depends on the inspected UI changes. If starting from `main`, confirm those prerequisites are integrated first. Do not silently merge/cherry-pick the 71-commit UI branch to manufacture a base.

## Review Focus

- A delayed exec channel callback after timeout/disposal must close that channel and must not close the terminal connection (Task 2).
- A missing `/proc` field, counter decrease, or unusable `df` section must produce a truthful unavailable/partial state, never a plausible zero (Task 3).
- A foreign client ID/session or obsolete stop request must not replace/cancel the current valid subscription (Task 4).
- An update or start reply from tab A after switching to B must neither redraw B nor revive A's sampler (Task 5).
- Removing the monitor provider/plugin or encountering an unsupported target must preserve typing, SFTP, and readiness (Tasks 4-6).
- A session fact must survive monitor-plugin removal, must not outlive the client that owns the session, and must not leave a `handshake` listener behind on a dropped client (Tasks 2 and 5).

## Task 2: Make SSH exec bounded and cancellable, and record the handshake

## Task 3: Implement the pure Linux collector

## Task 5: Add the ClientMonitor panel and the status bar session facts

**Interfaces:** `ClientMonitor extends Service` registers `clientMonitor`, injects only `clientView`, `clientTransport`, `clientTerminal`, and consumes `SshApi.monitor`. `ClientChrome` keeps its existing inject list and additionally consumes `SshApi.monitor.onSessionFacts`; it must not gain `clientMonitor`. `createMonitorPanel(element: HTMLElement, actions: { toggleExpanded(): void; togglePaused(): void; retry(): void }): MonitorPanel` lives in `monitor-panel.ts`. `MonitorPanel` provides `render(state: MonitorPanelState): void` and `dispose(): void`; define/export `MonitorPanelState` there with the states and snapshot/expanded/paused fields in design section 7. This view helper contains no transport, timers, or session policy.

```typescript
export interface MonitorPanelState {
  status: 'idle' | 'loading' | 'ready' | 'partial' | 'paused'
    | 'unsupported' | 'error' | 'disconnected' | 'stale'
  snapshot: MonitorSnapshot | null
  expanded: boolean
  paused: boolean
  message?: string
}
```

`idle` covers connecting/no session; `paused` is the tab's explicit manual pause preference, while status may also be paused because of document visibility/collapse. Defaults per tab are **expanded=false and paused=false**. Treat each snapshot as one observation, without combining fields from different timestamps. An error may retain the prior snapshot with its original timestamp and clear error/stale labeling.

Collapsed by default is not a cosmetic choice: the prototype draws two fixed bands on a session screen, this shell already draws three, and an expanded strip makes four, all of them taken from the terminal's height. The collapsed row still reports its last-update state and keeps collapse/pause/retry reachable, so a freshly opened session collects nothing until the user expands it, and expanding must not move focus out of the terminal.

`ClientChrome` gains the two session facts, and `ClientMonitor` does not: the cipher and the host key algorithm are constants for the life of a connection, so they belong in the status bar's prototype cell (`chacha20-poly1305 · ed25519 · 128 行`, whose third item this shell already reports as `status-size`) rather than in a polled row. `ClientChrome` subscribes to `SshApi.monitor.onSessionFacts`, adds the two cells, renders `cipher.clientToServer` and appends `→ cipher.serverToClient` only when the two directions differ, and keeps the third previously-empty cell, session uptime, empty — the snapshot's `uptimeSeconds` is the **host's** uptime, a different figure. It ignores facts whose `revision` is not greater than the one it already holds for that `sessionId`, buffers facts that arrive before `terminal:opened` for a session it has not seen, and drops facts for a session it never sees open. `ClientChrome` must not inject `clientMonitor`, and neither plugin may inject the other.

The existing lifecycle and Electron fixtures keep their windows hidden. Tests must control the document visibility getter and dispatch `visibilitychange` before asserting sampling, restore the getter afterward, and explicitly assert the hidden state stops sampling. Make this a test-only page setup, not a product flag that bypasses the visibility policy. Apply the same controlled visibility setup to Task 6's hidden browser fixtures.
